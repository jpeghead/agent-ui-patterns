# 02 · Permission with real scope

## The problem

An agent wants to run `rm -rf build/ .next/cache`. The usual prompt is the command and two buttons, Allow and Deny. The person has to decide, in a second, whether that command is safe, from the command alone. Most say Allow, because the alternative is to stop everything, and after a dozen prompts they say Allow to everything. The prompt has trained them to stop reading.

The worse version offers "Allow all" or "Don't ask again", which turns one decision into a standing policy the person did not mean to set.

## The principle

A permission prompt is a contract. It states what will be touched, whether it can be undone, and whether anything leaves the machine. It offers an allow exactly as narrow as the command, and a wider allow that is still precise ("this command, this session"), never a blanket yes. Deny is a real option, with its consequence stated, so choosing it is a decision and not a failure.

The person should be able to answer the prompt from the prompt. If they have to open a terminal to find out what `build/` contains, the prompt has failed.

## Anatomy

- **Who and why.** "Claude wants to run a command · to clear a stale build before the test run." The actor, the verb, and the reason the agent gives. The reason is the agent's, in one clause; it is not a justification essay.
- **The command**, verbatim, monospace, scrollable if long. Never summarized. Never truncated in the middle.
- **Touches.** Counts a person can feel: 2 directories, 1,204 files, 38 MB. A link to the list. The list is there for the one time in twenty it matters.
- **Reversible.** Yes or No, then why in one sentence. "Yes. Both are regenerated by the next build." If No, say what is lost.
- **Outside the repo.** Yes or No. Network, other folders, credentials. This is the line that separates a tidy-up from a leak.
- **Allow once.** The default focus. Runs this command, this time.
- **Allow this session**, with the exact command in the label. Not "allow rm", not "allow shell", the command. The rule it creates is shown in the session header and revocable in one click.
- **Deny**, styled as a real choice, not as the escape hatch. Its consequence appears after: "Claude will run the tests against the stale build and tell you if that mattered."
- **The receipt.** After the choice, one line: what was allowed, how long it ran, what asks again next time.

## States

| State | What shows |
|---|---|
| Asking | The contract and three choices; focus on Allow once |
| Allowed once | Receipt: ran in 0.3s; the next destructive command will ask again |
| Allowed for the session | Receipt: exactly this command, nothing broader; the rule and where to revoke it |
| Denied | Receipt: what the agent will do instead and what it will report |

There is no "allow forever". If a product needs standing rules, they are set in settings with the same contract shown, not in the moment of a prompt.

## Copy

- Lead with the actor and the verb: "Claude wants to run a command". Not "Permission required".
- The reason is one clause after a middle dot. It is the agent's stated purpose, so it can be wrong, and the person can see that it is wrong ("to clear a stale build" when the command deletes the source).
- "Touches", "Reversible", "Outside the repo" are the three labels. They are the three questions people actually have.
- Numbers, not adjectives. "1,204 files" not "many files". "38 MB" not "large".
- The session-allow button names the command. Long commands get the first thirty characters and an ellipsis, with the full text on hover and in the receipt.
- Deny's consequence is a promise the agent keeps: it says what it will do next.

## Keyboard and screen readers

- Focus lands on Allow once, the safest sufficient option. Enter allows once. Nothing destructive is the default.
- The three buttons are in one group in tab order; Deny is last, not hidden.
- "Show list" is a disclosure with `aria-expanded`.
- The receipt is `role="status"`, so the outcome is announced.

## Pitfalls seen in shipped products

- **Allow / Deny with nothing else.** The person decides blind.
- **"Don't ask again" in the prompt.** A standing policy set under time pressure.
- **A wildcard allow** ("allow all shell commands") offered as the convenient option. It is the dangerous option, labeled as convenient.
- **The command summarized** ("delete build artifacts"). The summary is the agent's interpretation; the person needed the command.
- **Deny that silently ends the task** with no account of what happens instead. People learn that Deny means failure and stop using it.
- **No receipt.** Ten prompts later nobody remembers what they allowed.
- **Rules you cannot find.** If a session rule exists, it is visible for the whole session and revocable where it is visible.

## Variations

- **File edits** instead of commands: the contract becomes the diff (files, lines added and removed), reversible (yes, via undo or git), outside the repo (no).
- **Network calls**: who it talks to (the host), what it sends (the fields), whether that leaves data behind.
- **Payments and sends**: never allowed for a session. Once, every time, with the amount or the recipient in the button.
- **Teams**: the receipt goes to the log that the whole team can read.
